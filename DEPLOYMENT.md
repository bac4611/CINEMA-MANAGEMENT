# Cinema production deployment

The root Maven project aggregates `backend`. Its existing resource configuration
copies `frontend/templates` and `frontend/static` into the executable Spring Boot
JAR. The root `Dockerfile` builds that JAR with Maven/Java 21, then copies only the
JAR into a Java 21 Alpine JRE image. The runtime uses UID/GID 10001, a read-only
filesystem and a temporary `/tmp`. There is one application image:
`bacdepzaiz7/cinema:<full-commit-sha>`.

The repository does not identify the production SQL Server location. The default
Compose file therefore connects to an **external, existing SQL Server database**.
It creates no database container, schema, seed data or database volume. No
application file uploads or other persistent application files were found; data
lives in SQL Server. Logs go to stdout with bounded Docker log rotation. H2
remains test-only, and the existing development profiles are unchanged.

## GitHub configuration

Use repository **Settings > Secrets and variables > Actions**. Keep database
credentials and application secrets exclusively in `/opt/cinema/.env` on the VPS.

| Secret | Value |
| --- | --- |
| `DOCKERHUB_USERNAME` | `bacdepzaiz7` |
| `DOCKERHUB_TOKEN` | Docker Hub access token allowed to push `bacdepzaiz7/cinema` |
| `VPS_HOST` | Actual VPS DNS name or IPv4 address |
| `VPS_USER` | Dedicated SSH deployment user with access to Docker and `/opt/cinema` |
| `VPS_SSH_KEY` | Private SSH key whose public key is installed for that user |
| `VPS_PORT` | Optional SSH port; defaults to `22` |
| `VPS_KNOWN_HOSTS` | Verified OpenSSH known_hosts entry for the VPS and SSH port |

Docker Hub credentials must be repository secrets so the publishing job can read
them. VPS credentials can be repository secrets or secrets in the `production`
GitHub environment. Create that environment, restrict it to `main`, and configure
reviewers if your release policy requires them. Create the repository variable
`ENABLE_VPS_DEPLOY` with value `true` **only after** completing VPS preparation.
Leave it absent or `false` while setting up infrastructure.

Obtain the VPS host public key through the provider console or another trusted
channel. On the VPS, display its fingerprint with:

```bash
sudo ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub
```

From a trusted workstation, collect an entry using
`ssh-keyscan -p "$VPS_PORT" -t ed25519 "$VPS_HOST" > cinema_known_hosts`, then use
`ssh-keygen -lf cinema_known_hosts` and compare fingerprints through that trusted
channel before saving the file contents as `VPS_KNOWN_HOSTS`. Scanning alone does
not establish trust. Nondefault ports require the `[host]:port` known_hosts form
generated by ssh-keyscan. The workflow requires strict host-key verification.

## Local build and Compose check

Run from the repository root:

```bash
bash ./mvnw --batch-mode --no-transfer-progress -pl backend -am verify
export CINEMA_IMAGE_TAG=$(git rev-parse HEAD)
docker build -t "bacdepzaiz7/cinema:$CINEMA_IMAGE_TAG" .
cp .env.example .env
chmod 600 .env
# Edit .env: set the real SQL Server URL/login/password and a random JWT_KEY.
# Set CINEMA_IMAGE_TAG there too for subsequent commands without this export.
docker compose --env-file .env -f compose.prod.yml config --quiet
docker compose --env-file .env -f compose.prod.yml up -d --wait --wait-timeout 180 cinema
docker compose --env-file .env -f compose.prod.yml ps
curl --fail http://127.0.0.1:8080/account/login
docker compose --env-file .env -f compose.prod.yml exec cinema \
  wget -q -O - http://127.0.0.1:8081/actuator/health
```

On Windows use `.\mvnw.cmd` for Maven. Compose requires a reachable SQL Server
with the application's schema already present. The H2 test database is not part
of the runtime image. Keep `production` active; never add `dev`, `development`
or `Development` on the VPS because development authentication can bypass
password checks and the `dev` profile seeds accounts. Generate `JWT_KEY` with
`openssl rand -hex 32`; keep it stable across releases. Put literal environment
values containing `$` or `#` in single quotes in `.env`. Do not print rendered
Compose configuration into CI logs; it contains credentials.

## Install Docker on Ubuntu

Use a supported 64-bit Ubuntu installation; published application images target
`linux/amd64`. Check for conflicting distribution Docker packages first and
follow the official upgrade guidance if Docker is already installed. The fresh
installation sequence from the [Docker Ubuntu guide](https://docs.docker.com/engine/install/ubuntu/) is:

```bash
sudo apt-get update
sudo apt-get install -y ca-certificates curl
sudo install -m 0755 -d /etc/apt/keyrings
sudo curl -fsSL https://download.docker.com/linux/ubuntu/gpg -o /etc/apt/keyrings/docker.asc
sudo chmod a+r /etc/apt/keyrings/docker.asc
sudo tee /etc/apt/sources.list.d/docker.sources > /dev/null <<EOF
Types: deb
URIs: https://download.docker.com/linux/ubuntu
Suites: $(. /etc/os-release && echo "${UBUNTU_CODENAME:-$VERSION_CODENAME}")
Components: stable
Architectures: $(dpkg --print-architecture)
Signed-By: /etc/apt/keyrings/docker.asc
EOF
sudo apt-get update
sudo apt-get install -y docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin
sudo systemctl enable --now docker
docker compose version
```

Use Compose v2 with `up --wait` and `--wait-timeout` (v2.20+ recommended).
The deploy script also requires Bash and `flock` from Ubuntu's `util-linux`.
For the dedicated deployment account, an administrator can run:

```bash
sudo usermod -aG docker "$VPS_USER"
sudo install -d -m 700 -o "$VPS_USER" -g "$(id -gn "$VPS_USER")" /opt/cinema
```

Set `VPS_USER` to your actual deployment account before those commands. Membership
in the Docker group grants administrative control over the host. Log out and
back in before checking `docker info` as that user. Install its authorized SSH
public key and verify key authentication before enabling CD.

## Prepare /opt/cinema and SQL Server

Transfer `compose.prod.yml`, `.env.example`, and `scripts/deploy.sh` from the
reviewed source checkout to `/opt/cinema`, preserving the `scripts` directory.
As the deployment user:

```bash
cd /opt/cinema
cp .env.example .env
chmod 600 .env
${EDITOR:-vi} .env
```

Set all required values in `.env`. For Linux containers use SQL authentication
with a dedicated application login, not the local development Windows native
authentication URL. Set `SPRING_DATASOURCE_URL` to:

```text
jdbc:sqlserver://<real-sql-server-dns>:1433;databaseName=MovieTicketDB;encrypt=true;trustServerCertificate=false
```

Replace the placeholder with your actual server name. The certificate must match
that name and chain to a CA trusted by Java. For a private CA, provision a Java
truststore on the VPS, mount it read-only into the container, and configure
`JAVA_TOOL_OPTIONS=-Djavax.net.ssl.trustStore=/run/certs/sqlserver.p12` (and its
password if required) in the VPS environment. Do not disable certificate
validation. Allow SQL Server TCP access only from the VPS/private network, and
ensure the container can resolve and reach it. Do not publish port 1433.

The database and schema must be provisioned independently by an administrator.
Review the repository's `database/` scripts against the target environment;
deployment never runs them. `production` fixes Hibernate DDL to `none` and SQL
initialization to `never`. Back up the database through your normal DBA process.

Configure SMTP, Google credentials/profile, and SePay variables from
`.env.example` as needed. Without SMTP, email verification/password reset cannot
send mail. JVM sessions and in-memory state are lost on application recreation;
users may need to log in again.

### If SQL Server should run on this VPS instead

This is an infrastructure choice that has not been supplied. Before using a local
SQL Server container, add a separately managed Compose file/service using a
supported Microsoft SQL Server Linux image, e.g.
`mcr.microsoft.com/mssql/server:2022-latest` (pin an approved CU/digest for
production). Check Microsoft's licensing, x86-64 support and memory requirements;
choose the appropriate `MSSQL_PID` and explicitly accept the EULA. Supply a strong
`MSSQL_SA_PASSWORD` through a protected VPS environment file, never in source.

Mount a named volume at `/var/opt/mssql` and join the database service and Cinema
to the same user-defined Docker network. For a separate Compose project, declare
that shared network as external in both files. Use a network alias such as
`sqlserver` in the application's JDBC URL. Define **no** database `ports` mapping.
Provision SQL Server's TLS certificate with a matching DNS name and configure
Java to trust its CA. Add an authenticated `SELECT 1` health check using the
image's sqlcmd tooling and validated TLS; use `depends_on: condition:
service_healthy` if both services share a Compose project, or wait for database
health separately if they do not. Provision the database/schema and least
privilege application login manually, then set the app's environment accordingly.
The app deployment script always targets only `cinema` with `--no-deps`, so the
database lifecycle and backups remain independent. Never remove its volume or
run `docker compose down -v` during deployment or rollback.

## Manual deployment, logs and rollback

If the Docker Hub repository is private, authenticate **on the VPS** once with a
read-only Docker Hub token using `docker login --username bacdepzaiz7
--password-stdin`, supplying the token through a secure local input mechanism.
CI's Docker login does not authenticate the VPS. Use a credential helper where
available. The full commit tag must already have been published by CI (or built
and pushed manually from that reviewed commit).

```bash
cd /opt/cinema
# Set this to a real published, full 40-character commit SHA:
export CINEMA_IMAGE_TAG='<published-commit-sha>'
bash scripts/deploy.sh "$CINEMA_IMAGE_TAG"

# Current status and logs (also use this export after reconnecting):
export CINEMA_IMAGE_TAG=$(cat .deployed-tag)
docker compose --env-file .env -f compose.prod.yml ps
docker compose --env-file .env -f compose.prod.yml logs --tail 100 -f cinema
docker logs --tail 100 "$(docker compose --env-file .env -f compose.prod.yml ps -q cinema)"
curl --fail --silent --show-error -o /dev/null http://127.0.0.1:8080/account/login
docker compose --env-file .env -f compose.prod.yml exec -T cinema \
  wget -q -O - http://127.0.0.1:8081/actuator/health/readiness

# Roll back both the image and the previous successful Compose configuration:
bash scripts/deploy.sh "$(cat .previous-tag)" .previous-compose.yml
```

Replace `<published-commit-sha>` before executing; it is documentation notation.
The script pulls the requested tag, recreates only `cinema`, and waits up to 180
seconds for the image health check, then requests HTTP readiness inside the
container. Both checks must pass. The private `/actuator/health` includes
database connectivity; SMTP health is disabled because it is optional. The
management port 8081 listens only on container loopback. No management port is
published. See [Spring Boot health documentation](https://docs.spring.io/spring-boot/reference/actuator/endpoints.html).

The first managed deployment has no rollback baseline. Afterwards, the script
saves `.deployed-tag`/`.deployed-compose.yml` and
`.previous-tag`/`.previous-compose.yml`. On deployment failure it attempts to
restore the last healthy image and Compose snapshot and still exits nonzero,
failing GitHub Actions. Keep previous image tags available in Docker Hub. The
script does not roll back database changes or `.env`; make those changes backward
compatible. It does not remove volumes, run cleanup/prune, or apply migrations.
One application container is recreated, so a brief interruption is expected.

## Automatic deployment

The existing **Cinema build** workflow in `.github/workflows/deploy.yml` retains
checkout, Java 21, `-pl backend -am verify`, H2 tests, and JAR/DLL artifact upload.
The separate **Cinema CI** workflow in `.github/workflows/ci.yml` is preserved.
Deployment control-flow checks also run against a fake Docker command via
`bash scripts/tests/deploy-test.sh`; they exercise successful releases, failed
health checks, HTTP readiness failures, failed pulls, first-release failure,
rollback failure and manual rollback without contacting any infrastructure.

1. PRs to `main`: test/package, upload artifacts, and build the Docker image.
   PRs never log in, push images, or deploy.
2. Pushes to `main`: after successful CI, build and push
   `bacdepzaiz7/cinema:${{ github.sha }}` with official Docker login/Buildx/build
   actions. Missing Docker Hub secrets fail the Docker job with an explicit error;
   deployment requires successful publishing and its returned image digest.
   There is no dependency on a mutable `latest` tag.
3. CD runs only after successful publishing, with `ENABLE_VPS_DEPLOY=true`.
   It validates all VPS secrets, uses strict SSH host-key verification, confirms
   `/opt/cinema/.env` exists, uploads deployment files into a commit/run-specific
   release directory, then runs the same deployment script on the VPS.
4. Manual **Run workflow** on `main` tests/builds/publishes. It deploys only if the
   operator explicitly selects the `deploy` input and the enable flag is true.
   Other branches cannot publish or deploy through this workflow.
5. Production jobs serialize and are not cancelled mid-deployment; the VPS script
   also takes a lock. Successful health checks are required for workflow success.

After completing all prerequisites, set `ENABLE_VPS_DEPLOY=true`, then use an
explicit manual run on `main` with `deploy=true` for the first deployment. Future
successful pushes to `main` deploy automatically. Set the variable to `false` to
disable future CD. This implementation does not perform a production deployment.

If `ENABLE_VPS_DEPLOY` is already true, set it to false before merging the new
workflow when production has not been approved or prepared: the merge itself
triggers a push to main and therefore automatic deployment when enabled. Prepare
`/opt/cinema/.env` first; CI uploads Compose and the deployment script, but never
creates database credentials or the VPS environment file. See
[the CI/CD audit and release checklist](docs/CICD-AUDIT.md).

## Firewall, reverse proxy and HTTPS

Allow inbound SSH only from approved administrative/CI sources as practical.
Allow public HTTP/HTTPS (80/443) to a host reverse proxy once configured. Keep
8080 bound to loopback and 8081/1433 unpublished. Docker-published ports can bypass
UFW rules; use explicit bind addresses and the appropriate Docker host firewall
rules as described in the [Docker Ubuntu firewall guidance](https://docs.docker.com/engine/install/ubuntu/#firewall-limitations).

For a future domain, configure DNS to the VPS, put Nginx/Caddy on the host in
front of `http://127.0.0.1:8080`, obtain a valid certificate, and redirect HTTP to
HTTPS. Forward the original Host, X-Forwarded-Proto and client address; overwrite
incoming forwarded headers at the proxy because Spring trusts those headers.
If the proxy is containerized, use a private shared network instead of its own
127.0.0.1. After HTTPS is ready set `SERVER_SERVLET_SESSION_COOKIE_SECURE=true`
in the VPS `.env`, and configure Google OAuth callbacks to your actual HTTPS
domain. No domain, certificate, VPS address, SQL Server host, or credentials
have been assumed.
